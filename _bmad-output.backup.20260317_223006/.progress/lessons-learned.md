## ✅ 成功经验（保持的做法）

### 1. CEO 指挥模式 + 异步通知

**做法：**
- 使用 `launch_async_process` 启动 AI 员工任务
- 启用 `--notify_on_complete true` 自动飞书通知
- CEO 确认进程启动后立即停止会话
- 收到通知后恢复会话验收

**效果：**
- ✅ 零轮询等待，Token 消耗降低 99%+
- ✅ 任务完成立即收到通知
- ✅ 支持多任务并行管理
- ✅ 会话连续性保持良好

**关键命令：**
```bash
launch_async_process \
  --command "cat /tmp/prompt.txt | claude -p '任务描述'" \
  --name "task-xxx" \
  --notify_on_complete true \
  --notify_message "自定义通知消息"
```

### 2. Story 开发会话隔离

**做法：**
- 每个 Story 在独立会话中完成
- Story 完成后开启新会话进行下一个 Story
- 使用 `/bmad-help` 扫描项目状态恢复上下文

**效果：**
- ✅ 避免上下文污染（开发代码消耗大量 Token）
- ✅ 保持每个 Story 的独立性和清晰度
- ✅ 降低 Token 消耗，提高效率
- ✅ 问题定位更容易（每个 Story 独立）

**工作流程：**
```
启动 Story → 确认进程 → 停止会话 → 等待通知 → 
收到通知 → 新会话恢复 → 验收 → 启动下一个 Story
```

### 3. 临时文件 + 管道传递提示词

**做法：**
- 复杂提示词写入临时文件
- 使用管道传递给 claude 命令
- 避免 shell 转义问题

**效果：**
- ✅ 支持多行提示词
- ✅ 支持任意特殊符号（$ ` " ' ${VAR}）
- ✅ 提示词可复用和版本控制
- ✅ 避免命令行转义错误

**示例：**
```bash
cat > /tmp/prompt.txt << 'EOF'
你的任务描述...
可以包含任何特殊符号
EOF
cat /tmp/prompt.txt | claude -p "按照上述提示执行"
```

## ⚠️ 遇到的问题与解决方案

### 问题 1: BMAD 渐进式进度保存不稳定

**现象：**
- BMAD 会话频繁重置（2-3 分钟）
- 进度保存丢失，需要重新输入

**原因：**
- BMAD 交互模式依赖会话状态
- 长对话上下文容易丢失

**解决方案：**
- ✅ 采用 `/bmad-help` 新会话策略
- ✅ 阶段完成后开启新会话
- ✅ 使用临时文件 + 管道一次性传递完整信息
- ✅ 进度文档独立记录（不依赖 BMAD）

**教训：**
> 内容明确时使用临时文件 + 管道一次性传递完整信息更可靠，避免依赖 BMAD 的渐进式交互。

---

### 问题 2: CEO 当面执行效率低

**现象：**
- 使用 `execute_shell_command` 调用 Claude
- CEO 会话被阻塞，无法处理其他任务
- 员工无法汇报工作（通知被卡住）

**原因：**
- 同步执行阻塞主进程
- Hook 通知机制被阻塞

**解决方案：**
- ✅ 强制使用 `launch_async_process`
- ✅ 禁止 `execute_shell_command` 调用 Claude
- ✅ CEO 确认进程启动后立即停止会话

**教训：**
> 避免当面执行。CEO 动口不动手 — 发布指令后等待结果，不阻塞主进程。

---

### 问题 3: 提示词包含特殊符号时转义错误

**现象：**
- 提示词包含 $ ` " ' 等符号时命令执行失败
- 多行提示词难以处理

**原因：**
- shell 命令行转义复杂
- 不同符号需要不同转义方式

**解决方案：**
- ✅ 使用临时文件 + 管道方式
- ✅ HEREDOC 语法避免转义（`<< 'EOF'`）
- ✅ 简单提示词用 echo 单行命令

**教训：**
> 💡 提示词传递技巧：使用管道 + 临时文件避免特殊符号问题

---

### 问题 4: 等待模式选择困难

**现象：**
- 不确定何时应该停止会话
- 担心停止后错过通知
- 轮询等待消耗 Token

**原因：**
- 等待策略不明确
- Hook 通知机制不熟悉

**解决方案：**
- ✅ 明确原则：没有其他任务时才停止会话
- ✅ 启用自动通知，零轮询等待
- ✅ 使用 `view_async_processes` 确认进程状态

**决策流程：**
```
启动任务 → 还有其他任务？→ 是 → 继续执行
                      ↓ 否
                  停止会话，等待通知
```

**教训：**
> 不是每次 launch_async_process 后都必须立即停止！只有没有其他任务可做，只剩下等待 Hook 通知时，才需要停止会话。

---

### 问题 5: BMAD 输出文档元数据保护

**现象：**
- 直接修改 BMAD 文档导致元数据不一致
- `stepsCompleted` 等 frontmatter 与实际不符
- BMAD 会话恢复时状态错误

**原因：**
- BMAD 文档包含自动维护的元数据
- 人工修改容易遗漏

**解决方案：**
- ✅ 严禁直接修改 `_bmad-output/` 文档
- ✅ 通过 BMAD 会话本身进行修改
- ✅ 进度文档独立记录在 `.progress/` 目录

**教训：**
> BMAD 输出文档保护：严禁直接修改 `_bmad-output/` 下的 BMAD 输出文档（含 frontmatter 元数据），通过 BMAD 会话本身进行修改。

## 🎓 学习收获

### 对 BMAD 框架的理解

1. **BMAD 是流程框架，不是代码生成器**
   - 价值在于结构化思考和文档产出
   - 代码实现需要 AI 员工配合

2. **渐进式 vs 一次性传递**
   - 渐进式适合探索性任务
   - 一次性传递适合内容明确的任务

3. **会话管理是关键**
   - 长对话容易丢失上下文
   - 阶段化 + 新会话是可靠策略

### 对 CEO 指挥模式的理解

1. **动口不动手**
   - CEO 负责决策和验收
   - 员工负责执行和实现

2. **异步通知是核心**
   - 轮询等待效率低、Token 消耗高
   - Hook 通知机制是最佳实践

3. **会话连续性**
   - `--resume` 保持多轮对话上下文
   - 新会话避免上下文污染

### 对安全系统开发的理解

1. **安全基础先行**
   - TEE、密钥派生先完成
   - 上层应用依赖稳定基础

2. **测试驱动安全**
   - 安全功能必须有完整测试
   - 回归测试保证不引入漏洞

3. **文档即规范**
   - 安全设计文档是开发依据
   - API 文档是使用规范

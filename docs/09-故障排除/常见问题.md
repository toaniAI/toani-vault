## 安装部署类

### 1. Docker 容器启动失败怎么办？

**问题描述**：执行 `docker-compose up` 或 `docker run` 时容器无法正常启动。

**可能原因**：

- 端口被占用
- 环境变量配置错误
- 依赖服务未就绪
- 资源不足（内存/CPU）
- 镜像损坏

**排查步骤**：

1. 查看容器日志：

```bash
docker logs <container_id>
docker logs credbridge-api  # 具体容器名
```

2. 检查端口占用：

```bash
lsof -i :8080  # 替换为实际端口
netstat -tlnp | grep 8080
```

3. 验证环境变量：

```bash
docker inspect <container_id> | grep -A 20 Env
```

4. 检查依赖服务状态：

```bash
docker-compose ps
docker network inspect credbridge-network
```

5. 查看系统资源：

```bash
docker stats
free -h
```

**解决方案**：

- **端口冲突**：修改 `docker-compose.yml` 中的端口映射或停止占用端口的服务
- **环境变量错误**：检查 `.env` 文件，确保所有必需变量已设置
- **依赖服务**：确保数据库、Redis 等服务先启动并健康
- **资源不足**：增加 Docker 资源限制或关闭其他容器
- **镜像问题**：重新构建或拉取镜像

```bash
docker-compose build --no-cache
docker-compose pull
```

### 2. Intel SGX 驱动如何安装？

**问题描述**：在启用 TEE 功能时，系统提示找不到 SGX 设备或驱动未安装。

**可能原因**：

- CPU 不支持 SGX
- BIOS 中 SGX 未启用
- SGX 驱动未安装
- 内核模块未加载

**排查步骤**：

1. 检查 CPU 是否支持 SGX：

```bash
grep -o sgx /proc/cpuinfo
lscpu | grep SGX
```

2. 检查 BIOS 设置：

- 重启进入 BIOS
- 查找 "Intel SGX" 或 "Software Guard Extensions"
- 设置为 "Enabled" 或 "Software Controlled"

3. 检查 SGX 驱动：

```bash
ls -l /dev/sgx
ls -l /dev/sgx/enclave
```

4. 检查内核模块：

```bash
lsmod | grep sgx
modprobe sgx_enclave
```

**解决方案**：

**Ubuntu 20.04+ 安装 SGX 驱动**：

```bash
# 添加仓库
wget -qO - https://download.01.org/intel-sgx/sgx_repo/ubuntu/intel-sgx-deb.key | sudo apt-key add -
echo 'deb [arch=amd64] https://download.01.org/intel-sgx/sgx_repo/ubuntu focal main' | sudo tee /etc/apt/sources.list.d/intel-sgx.list

# 安装驱动
sudo apt update
sudo apt install libsgx-enclave-common libsgx-urts libsgx-dcap-ql

# 加载内核模块
sudo modprobe sgx_enclave
sudo modprobe sgx_vepc

# 验证安装
ls -l /dev/sgx
```

**CentOS/RHEL 安装**：

```bash
sudo yum install sgx-dcap-pcl sgx-dcap-ql sgx-dcap-quote-verify
```

**Docker 容器中使用 SGX**：

```yaml
# docker-compose.yml
services:
  credbridge:
    devices:
      - /dev/sgx/enclave:/dev/sgx/enclave
      - /dev/sgx/provision:/dev/sgx/provision
    privileged: true # 或使用特定的 capabilities
```

### 3. 数据库连接失败如何排查？

**问题描述**：应用无法连接到 PostgreSQL 数据库，出现连接超时或认证失败错误。

**可能原因**：

- 数据库服务未启动
- 连接参数错误（主机、端口、数据库名）
- 认证失败（用户名、密码）
- 网络问题（防火墙、安全组）
- 连接池耗尽

**排查步骤**：

1. 检查数据库服务状态：

```bash
# Docker 环境
docker-compose ps db
docker logs credbridge-db

# 系统服务
systemctl status postgresql
```

2. 验证连接参数：

```bash
# 从应用日志查看连接字符串
docker logs credbridge-api | grep DATABASE_URL

# 测试连接
psql -h localhost -U credbridge -d credbridge
```

3. 检查网络连通性：

```bash
telnet db-host 5432
nc -zv db-host 5432
```

4. 查看数据库日志：

```bash
# Docker
docker exec -it credbridge-db tail -f /var/log/postgresql/postgresql.log

# 系统
sudo tail -f /var/log/postgresql/postgresql-14-main.log
```

5. 检查连接池：

```sql
-- 查看当前连接数
SELECT count(*) FROM pg_stat_activity;

-- 查看最大连接数
SHOW max_connections;
```

**解决方案**：

- **服务未启动**：`docker-compose up -d db` 或 `systemctl start postgresql`
- **参数错误**：检查 `.env` 文件中的 `DATABASE_URL`
- **认证失败**：重置数据库密码

```sql
ALTER USER credbridge WITH PASSWORD 'new_password';
```

- **网络问题**：检查防火墙规则和安全组设置
- **连接池耗尽**：增加 `max_connections` 或优化应用连接池配置

**相关文档**：[数据库连接问题.md](./数据库连接问题.md)

### 4. 端口冲突如何解决？

**问题描述**：启动服务时提示 "Address already in use" 或 "Port binding failed"。

**可能原因**：

- 同一服务已在运行
- 其他应用占用目标端口
- 端口处于 TIME_WAIT 状态

**排查步骤**：

1. 查找占用端口的进程：

```bash
# Linux/macOS
lsof -i :8080
netstat -tlnp | grep 8080
ss -tlnp | grep 8080

# 查看进程详情
ps aux | grep <pid>
```

2. 检查是否有残留进程：

```bash
ps aux | grep credbridge
ps aux | grep cargo  # Rust 开发时
```

3. 查看端口状态：

```bash
netstat -an | grep 8080
```

**解决方案**：

**方案 1：停止占用进程**

```bash
# 温和方式
kill <pid>

# 强制方式
kill -9 <pid>

# Docker 容器
docker stop <container_id>
```

**方案 2：修改应用端口**

```bash
# 修改环境变量
export API_PORT=8081

# 或修改配置文件
# config/app.toml
[server]
port = 8081
```

**方案 3：等待 TIME_WAIT 结束**

```bash
# 查看 TIME_WAIT 连接
netstat -an | grep TIME_WAIT

# 或修改内核参数（谨慎）
sudo sysctl -w net.ipv4.tcp_tw_reuse=1
```

**方案 4：Docker 端口映射调整**

```yaml
# docker-compose.yml
ports:
  - "8081:8080" # 主机端口：容器端口
```

**预防措施**：

- 使用进程管理工具（systemd、supervisor）
- 实现优雅关闭
- 添加健康检查

### 5. Token 验证失败可能的原因？

**问题描述**：API 请求返回 401 Unauthorized 或 Token 验证错误。

**可能原因**：

- Token 过期
- Token 签名无效
- Token 被篡改
- 密钥不匹配
- Token 格式错误

**排查步骤**：

1. 检查 Token 有效期：

```bash
# 解码 PASETO Token（需要密钥）
# 查看 payload 中的 exp 字段
```

2. 验证 Token 格式：

```bash
# PASETO v4.local 格式应以 v4.local. 开头
echo $TOKEN | cut -d'.' -f1-2
```

3. 检查服务器密钥配置：

```bash
# 查看日志中的密钥加载信息
docker logs credbridge-api | grep -i "key\|token"
```

4. 查看认证日志：

```bash
docker logs credbridge-api | grep -i "auth\|unauthorized"
```

**解决方案**：

- **Token 过期**：重新获取 Token（见问题 7）
- **密钥不匹配**：确保所有服务实例使用相同的密钥

```bash
# 检查环境变量
echo $PASETO_SECRET_KEY
```

- **Token 格式错误**：确保请求头格式正确

```bash
curl -H "Authorization: Bearer <token>" ...
```

- **签名无效**：使用正确的密钥重新生成 Token

**调试工具**：

```rust
// 使用 pasetors 库验证
use pasetors::{local::decrypt, keys::SymmetricKey, version4::V4};

let key = SymmetricKey::<V4>::from(key_bytes);
let claims = decrypt(&token, &key, None, None)?;
```

### 6. Scope 权限不足如何处理？

**问题描述**：API 请求返回 403 Forbidden，提示权限不足或 scope 不匹配。

**可能原因**：

- Token 中缺少必需的 scope
- Scope 名称不匹配
- 资源不属于当前用户
- 角色权限配置错误

**排查步骤**：

1. 检查 Token 中的 scopes：

```bash
# 解码 Token 查看 scopes
# scopes 通常在 claims 中
```

2. 查看 API 要求的 scope：

```bash
# 查看 API 文档或源码
grep -r "require_scope" src/api/
```

3. 验证用户角色：

```sql
SELECT u.email, r.name as role
FROM users u
JOIN user_roles ur ON u.id = ur.user_id
JOIN roles r ON ur.role_id = r.id
WHERE u.id = '<user_id>';
```

4. 检查审计日志：

```sql
SELECT * FROM audit_logs
WHERE event_type = 'authorization_failure'
ORDER BY created_at DESC
LIMIT 10;
```

**解决方案**：

- **缺少 scope**：重新申请包含正确 scope 的 Token

```bash
curl -X POST https://api.credbridge/auth/token \
  -d "scope=credentials:read credentials:write"
```

- **角色权限不足**：联系管理员提升权限

```sql
-- 添加角色（需要管理员权限）
INSERT INTO user_roles (user_id, role_id)
VALUES ('<user_id>', '<role_id>');
```

- **资源不属于用户**：检查资源所有权

```sql
SELECT owner_id FROM credentials WHERE id = '<cred_id>';
```

### 7. Privy 钱包连接失败怎么办？

**问题描述**：使用 Privy 进行钱包认证时，钱包连接失败或无法获取 Privy Token。

**可能原因**：

- 钱包扩展未安装或未启用
- 网络连接问题
- Privy App ID 配置错误
- 钱包不支持所选链
- 浏览器兼容性问题

**排查步骤**：

1. 检查钱包扩展状态：
   - 确保 MetaMask、WalletConnect 或其他钱包扩展已安装并启用
   - 检查钱包是否锁定（需要解锁）

2. 验证网络连接：

```bash
# 检查 Privy 服务状态
curl -I https://auth.privy.io
```

3. 检查 Privy 配置：

```javascript
// 确认 Privy App ID 正确
const privy = new PrivyProvider({
  appId: "your-app-id", // 检查是否与后端配置一致
});
```

4. 检查浏览器兼容性：
   - Privy 支持现代浏览器（Chrome、Firefox、Safari、Edge）
   - 确保浏览器版本最新

**解决方案**：

- **钱包未安装**：引导用户安装支持的钱包（MetaMask、WalletConnect 等）
- **网络问题**：检查网络代理设置，确保能访问 Privy 服务
- **配置错误**：确认前端 `PRIVY_APP_ID` 与后端 `PRIVY_APP_ID` 一致
- **链不支持**：确保钱包已添加目标网络（如 Ethereum、Polygon 等）

**调试工具**：

```javascript
// 前端调试
import { PrivyProvider } from "@privy-io/react-auth";

// 监听连接状态
privy.on("connection:failed", (error) => {
  console.error("Wallet connection failed:", error);
});
```

### 8. 会话过期如何恢复？

**问题描述**：Session Token 过期，API 请求返回 401 Unauthorized。

**可能原因**：

- Session Token 超过有效期（默认 24 小时）
- 会话被主动撤销（logout）
- Token 被加入黑名单
- 用户状态变更（禁用、删除）

**解决方案**：

**方法 1：重新创建会话**

```bash
# 使用 Privy Token 重新创建会话
curl -X POST https://api.credbridge/api/v1/auth/session \
  -H "Content-Type: application/json" \
  -d '{
    "privy_access_token": "<privy_token_from_frontend>"
  }'
```

响应：

```json
{
  "user": { ... },
  "session": {
    "id": "uuid",
    "session_token": "new_session_token",
    "expires_at": "2024-03-21T00:00:00Z",
    "mfa_status": "not_required"
  },
  "membership": { ... }
}
```

**方法 2：前端自动恢复**

```typescript
// 使用 Privy React SDK 自动恢复
import { usePrivy } from "@privy-io/react-auth";

function App() {
  const { authenticated, user, login } = usePrivy();

  // 当会话过期时，Privy 会自动刷新
  // 只需再次调用 /auth/session 创建新会话
}
```

**最佳实践**：

1. **前端自动处理**：Privy SDK 会自动管理 Token 刷新

```typescript
// 在会话过期时自动重新获取 Privy Token
useEffect(() => {
  if (authenticated && user) {
    const privyToken = user.accessToken;
    // 调用后端 /auth/session 创建会话
    createSession(privyToken);
  }
}, [authenticated, user]);
```

2. **错误处理**：捕获 401 错误并触发重新认证

```typescript
// Axios 拦截器示例
axios.interceptors.response.use(
  (response) => response,
  async (error) => {
    if (error.response?.status === 401) {
      // 触发 Privy 重新认证
      await login();
    }
    return Promise.reject(error);
  },
);
```

3. **会话状态管理**：使用 Zustand 或 React Context 管理会话状态

### 9. MFA 设置遇到问题怎么办？

**问题描述**：设置多因素认证（MFA）时遇到错误或验证失败。

**可能原因**：

- TOTP 应用未正确配置
- 时间同步问题
- MFA Secret 获取失败
- 验证码输入错误

**解决方案**：

**配置 TOTP 应用**：

1. 使用 Google Authenticator、Authy 或 1Password
2. 扫描二维码或手动输入 Secret Key
3. 确保设备时间与服务器时间同步

**时间同步检查**：

```bash
# 检查服务器时间
date

# 同步系统时间（Linux）
sudo ntpdate -s time.nist.gov
```

**验证码问题排查**：

- TOTP 验证码有 30 秒有效期
- 确保输入的是当前显示的验证码
- 如果连续失败，可能需要重新配置 MFA

**禁用/重置 MFA**（管理员操作）：

```sql
-- 查看用户 MFA 状态
SELECT id, mfa_enabled, mfa_secret FROM users WHERE id = '<user_id>';

-- 禁用 MFA（需要管理员权限）
UPDATE users SET mfa_enabled = false, mfa_secret = NULL WHERE id = '<user_id>';
```

### 10. 邀请 Token 无效如何处理？

**问题描述**：使用邀请 Token 加入租户时，提示 Token 无效或已过期。

**可能原因**：

- 邀请 Token 已过期（默认 7 天有效期）
- 邀请已被消费
- Token 格式错误
- 邀请目标邮箱与当前用户不匹配

**排查步骤**：

1. 验证 Token 格式：

```bash
# 邀请 Token 应为 UUID 格式
# 示例：018f1b4e-7e9e-7f3a-8b5c-2d4e6f8a0b2c
```

2. 检查邀请状态（数据库查询）：

```sql
SELECT id, status, expires_at, consumed_at, invited_email
FROM invitations
WHERE id = '<invitation_token>';
```

3. 检查 Token 是否过期：

```sql
SELECT expires_at, NOW() as current_time
FROM invitations
WHERE id = '<invitation_token>';
```

**解决方案**：

- **Token 过期**：联系管理员重新发送邀请
- **已被消费**：邀请已使用，无法再次加入，联系管理员处理
- **邮箱不匹配**：确保使用与邀请邮箱一致的 Privy 身份登录

**管理员操作**：

```sql
-- 创建新邀请
INSERT INTO invitations (id, tenant_id, role, invited_email, expires_at, created_by)
VALUES (
  gen_random_uuid(),
  '<tenant_id>',
  'member',
  'user@example.com',
  NOW() + INTERVAL '7 days',
  '<admin_user_id>'
);

-- 查看邀请历史
SELECT id, invited_email, status, created_at, expires_at
FROM invitations
WHERE tenant_id = '<tenant_id>'
ORDER BY created_at DESC;
```

**消费邀请 API**：

```bash
# 正确的消费邀请方式
curl -X POST https://api.credbridge/api/v1/auth/invitations/consume \
  -H "Authorization: Bearer <session_token>" \
  -H "Content-Type: application/json" \

### 15. Sandbox 操作超时怎么办？

**问题描述**：Sandbox 操作执行超时，返回 timeout 错误。

**可能原因**：

- 操作过于复杂

- 死锁或阻塞

```

4. 查看操作日志：

```bash

```

**解决方案**：

**方案 1：增加超时时间**

```bash

```

**方案 2：优化操作**

- 使用异步执行
- 实现分页处理

**方案 3：资源隔离**

```yaml
# 为不同用户分配独立 sandbox
sandbox_per_user: true
```

**方案 4：实现重试机制**

```rust
use tokio::time::{timeout, Duration};

async fn execute_with_retry<F, T>(operation: F, max_retries: u32) -> Result<T>
where
    F: Fn() -> Future<Output = Result<T>>,
{
    for attempt in 0..max_retries {
        match timeout(Duration::from_secs(30), operation()).await {
            Ok(result) => return result,
            Err(_) => {
                if attempt == max_retries - 1 {
                    return Err(Error::Timeout);
                }
                tokio::time::sleep(Duration::from_secs(2)).await;
            }
        }
    }
    unreachable!()
}
```

### 20. 数据库查询慢如何排查？

**问题描述**：数据库查询响应时间超过预期。

**排查步骤**：

1. 启用慢查询日志：

```sql
-- PostgreSQL
ALTER SYSTEM SET log_min_duration_statement = 1000;  -- 记录>1s 的查询
SELECT pg_reload_conf();
```

2. 分析查询计划：

```sql
EXPLAIN ANALYZE
SELECT * FROM credentials
WHERE name = 'test'
ORDER BY created_at DESC;
```

3. 查看表统计：

```sql
SELECT
  schemaname,
  tablename,
  seq_scan,
  seq_tup_read,
  idx_scan,
  idx_tup_fetch
FROM pg_stat_user_tables
ORDER BY seq_scan DESC;
```

4. 检查锁：

```sql
SELECT
  blocked_locks.pid AS blocked_pid,
  blocking_locks.pid AS blocking_pid,
  blocked_activity.query AS blocked_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
WHERE NOT blocked_locks.GRANTED;
```

**解决方案**：

**添加索引**：

```sql
-- 常用查询字段
CREATE INDEX idx_credentials_name ON credentials(name);
CREATE INDEX idx_credentials_type ON credentials(credential_type);
CREATE INDEX idx_credentials_created ON credentials(created_at DESC);

-- 复合索引
CREATE INDEX idx_credentials_user_status
ON credentials(user_id, status);
```

**优化查询**：

```sql
-- 避免 SELECT *
SELECT id, name, credential_type FROM credentials WHERE ...

-- 使用 EXISTS 代替 IN
SELECT * FROM credentials c
WHERE EXISTS (
  SELECT 1 FROM users u WHERE u.id = c.user_id
);

-- 避免函数索引
-- 错误：WHERE DATE(created_at) = '2024-01-01'
-- 正确：WHERE created_at >= '2024-01-01' AND created_at < '2024-01-02'
```

**表维护**：

```sql
-- 清理死元组
VACUUM ANALYZE credentials;

-- 重建索引
REINDEX TABLE credentials;
```

// 使用零拷贝

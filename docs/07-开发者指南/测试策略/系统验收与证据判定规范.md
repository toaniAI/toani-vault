# CredBridge 系统验收与证据判定规范

## 1. 文档定位

本文档定义 CredBridge 在系统验收、集成评估、运行时验证中的统一规范。它不回答“功能怎么开发”，只回答“什么证据可以支持什么事实判定，以及判定必须如何产生”。

## 2. 术语与判定对象

### 2.1 基本定义

- **观察（Observation）**：执行过程中直接采集到的原始现象，如 HTTP 状态码、页面文本、日志、trace、截图、审计记录、指标。
- **断言（Assertion）**：对单个观察或观察组合施加的明确判定规则。
- **证据（Evidence）**：可以复核、可追溯、带时间与环境上下文的观察集合。
- **事实（Fact）**：经足够证据支持、且判定边界明确的结论。
- **解释（Interpretation）**：对事实成因、影响或设计意图的说明，不可替代事实本身。
- **验证器（Validator）**：执行某类验证并输出标准化证据包的工具或流程。

### 2.2 判定对象

验收阶段允许被判定的对象只有以下几类：

- **契约是否成立**：接口、消息、页面对外交互约定是否满足
- **行为是否成立**：系统在给定输入与前置条件下是否产生预期输出
- **约束是否成立**：隔离、权限、速率、资源限制、审计、TEE 模式等约束是否生效
- **观测是否充分**：失败时是否能定位到失败归因，而不是只有“失败了”

## 3. 验收必须坚守的原则

### 3.1 事实优先，解释后置

- 验收报告必须先写事实，再写解释。
- 任何“看起来正常”“大概率没问题”“代码里应该如此”都不是事实。
- 未提供证据链的结论，默认视为未证实。

### 3.2 以用户与外部契约为中心

- 系统验收验证的是对外承诺，不是内部实现细节。
- 页面验收必须基于用户可见行为、可操作元素、可观察结果。
- API 验收必须基于请求、响应、状态码、错误语义、审计副作用。

### 3.3 证据与结论分层

- 单元测试、静态检查、review findings 只能证明“局部质量”或“风险存在/不存在的线索”。
- 集成测试、契约测试、E2E、运行时观测才能支持系统级事实。
- 任何低层证据都不能越级替代高层验收结论。

### 3.4 不允许单点证据独裁

- 不允许用一个分数、一个模型输出、一次通过、一次截图，直接宣告系统可验收。
- 同一项高风险结论至少需要两类不同来源证据互相支撑。
- 安全、隔离、TEE、审计完整性类结论，必须包含运行时证据。

### 3.5 假阳性与假阴性同等重要

- 通过但实际有问题，属于假阳性。
- 失败但系统无问题，属于假阴性。
- 验收规范必须同时降低两者，不能只追求“多报问题”或“少报问题”。

### 3.6 可复现优先于一次成功

- 无法复现的成功，证据价值有限。
- 无法复现的失败，默认先归类为“待分类异常”，不得直接归因为产品缺陷。
- 所有关键验收结论应具备重放路径。

### 3.7 人工确认边界必须保留

- 视觉语义、合规解释、业务合理性、某些 TEE/硬件证明可信性判断，允许并且应该保留人工确认环节。
- AI 或自动化只能给出证据与候选结论，不得越权替代最终责任人签署。

## 4. 测试 AI 应具备的素质

测试 AI 不是脚本生成器，而是“证据收集与事实判定代理”。必须具备以下素质：

### 4.1 区分事实与猜测

- 明确标注“已观测”“已断言”“推测”“待人工确认”
- 不把日志猜测包装成事实
- 不把代码阅读结论包装成运行时结论

### 4.2 对误判敏感

- 主动识别 flaky、环境污染、数据竞争、缓存污染、时钟漂移、依赖抖动
- 遇到一次失败时先做复核，不直接定性
- 遇到一次通过时先看是否满足最小证据包

### 4.3 重视契约与可追溯性

- 所有验证动作都应有输入契约、输出契约、上下文信息、工件落盘位置
- 结果必须能回答：谁执行、何时执行、在哪个环境、针对哪个版本、拿到了什么证据

### 4.4 不迷信单一模型和单一评分

- LLM 评审结果只能作为风险信号，不能单独作为验收通过依据
- 安全分、质量分、健康分可以用于排序，不可直接替代验收结论

### 4.5 主动暴露边界

- 能明确说出“这项只能证明到哪一层”
- 能明确说出“这项目前必须人工确认”
- 能明确说出“当前证据不足，不能判定”

## 5. 必须严格遵循的方法论

### 5.1 Claim-Driven Acceptance

所有验收从 **Claim（待证实声明）** 出发，而不是从脚本出发。

每条 Claim 必须写成：

1. **主体**：哪个系统或子系统
2. **条件**：在什么输入、环境、身份、数据前置下
3. **行为/约束**：必须发生什么，或必须不发生什么
4. **可观察结果**：从哪里拿到结果
5. **失败后果**：失败意味着什么等级的问题

示例：

- “在 `TEE_MODE=hardware` 且远程证明服务可用时，仪表板与 attestation API 返回的运行态应一致，且存在可追溯审计记录。”
- “当租户 A 持有凭证时，租户 B 通过任何 API、前端路径、会话复用或缓存残留均不得读取该凭证明文。”

### 5.2 分层验收模型

系统验收采用五层证据模型：

1. **Review / Static**：代码评审、配置检查、Schema/OAS 对照、静态规则
2. **Contract**：前后端、SDK 与 API、服务与外部依赖的输入输出契约
3. **Integration**：真实依赖组合后的行为验证
4. **E2E**：用户路径、跨组件闭环、关键业务旅程
5. **Runtime**：真实部署环境中的日志、trace、metrics、审计、TEE 运行态证明

约束：

- 上层失败不能被下层通过抵消。
- 下层通过不能越级证明上层成立。
- 最终验收结论必须至少覆盖 `Contract + Integration + E2E + Runtime` 四层。

### 5.3 统一验证器接口

所有验证器必须抽象为统一接口，输出标准化证据包。推荐最小结构如下：

```json
{
  "validator_id": "e2e.dashboard.runtime.v1",
  "layer": "runtime",
  "claim_id": "CLAIM-TEE-001",
  "target": "https://dev-credbridge.bitkinetic.com/dashboard",
  "inputs": {
    "actor": "qa-ai",
    "tenant": "tenant-a",
    "build_ref": "git_sha_or_tag",
    "env": "dev-tee"
  },
  "preconditions": [
    "authenticated",
    "seed_data_loaded",
    "clock_synced"
  ],
  "observations": [],
  "assertions": [],
  "artifacts": [],
  "status": "passed|failed|inconclusive",
  "failure_class": "product|env|test_harness|data|flake|unknown",
  "started_at": "ISO-8601",
  "finished_at": "ISO-8601",
  "replay": {
    "command": "or procedure reference",
    "seed": "optional"
  }
}
```

统一要求：

- 必须带 `claim_id`
- 必须带 `layer`
- 必须带 `failure_class`
- 必须能关联到工件
- 必须可复核，不允许只输出自然语言总结

### 5.4 断言设计方法

每条断言必须满足：

- **单一职责**：一次断言只判定一个事实
- **显式 Oracle**：清楚写出“什么算通过”
- **显式边界**：清楚写出“什么不在本断言能力范围内”
- **带容差**：性能、延迟、采样类断言必须有明确阈值与采样窗口
- **带负例**：安全、权限、隔离类必须包含拒绝性断言

不合格断言示例：

- “页面看起来没问题”
- “响应基本正确”
- “性能还行”

合格断言示例：

- “`GET /api/v1/attestation` 返回 `200`，且 `runtime_mode`、`quote_status`、`timestamp` 字段齐全，字段语义与仪表板展示一致。”
- “在租户 B token 下访问租户 A credential 明文接口，必须返回 `403` 或等价拒绝响应，且审计日志记录越权尝试。”

### 5.5 失败分类方法

所有失败必须先分类，再处置。标准分类如下：

| 分类 | 定义 | 是否可直接判产品失败 |
|------|------|----------------------|
| `product` | 产品真实缺陷 | 是 |
| `env` | 环境不可用、配置错误、依赖故障 | 否 |
| `test_harness` | 用例、脚本、夹具、验证器自身问题 | 否 |
| `data` | 测试数据脏污、种子错误、前置数据不满足 | 否 |
| `flake` | 非确定性失败，重跑结果不稳定 | 否 |
| `unknown` | 当前证据不足，尚未归因 | 否 |

强制规则：

- 单次失败默认不允许直接记为 `product`，除非证据已足够排除环境、脚本和数据问题。
- `unknown` 不能进入最终通过结论。
- `flake` 不能被忽略，必须记录抖动频率、重试结果、关联工件。

### 5.6 证据权重与边界

#### Review Findings

- 只能证明“存在风险信号”或“发现设计/实现疑点”
- 不能单独证明“系统行为成立”
- 不能单独证明“运行时安全性成立”

#### Test Result

- 可以证明某一层级、某一环境、某一输入下的行为成立或不成立
- 结论边界受测试层级和依赖替身影响
- 含 mock/stub 的结果，不得外推为真实环境结论

#### Runtime Evidence

- 能证明“该部署环境在该时间点的真实运行状态”
- 不能单独说明根因，也不能替代源代码层面的修复正确性证明
- 对 TEE、审计、资源限制、会话状态、监控一致性等结论权重最高

#### 人工确认

- 用于视觉语义、合规描述、硬件可信链解释、异常归因收敛
- 人工确认不是“拍脑袋批准”，也必须绑定证据

### 5.7 运行时可观测性方法

验收阶段必须把日志、指标、链路作为同一证据包的一部分。OpenTelemetry 的通用信号模型可作为统一抽象：

- `Traces`：一条请求如何穿过系统
- `Metrics`：运行时的数量、耗时、资源变化
- `Logs`：离散事件记录

验收要求：

- 每个关键请求至少能关联到 `request_id`、`trace_id` 或等价关联键
- 日志与 trace、metrics 必须可关联，不能只保留孤立文本日志
- 性能和资源结论必须带时间窗口、样本数、分位数或聚合口径

## 6. 验收与评估时必须遵循的操作和动作

### 6.1 验收前固定动作

1. 记录后端 Git 提交号、前端 Git 提交号、部署环境标识、执行时间、执行人。
2. 记录 `TEE_MODE`、是否硬件 SGX、是否 simulation、远程证明依赖状态。
3. 固化验收 Claim 清单，未列入 Claim 的内容不得临时用“感觉正常”补判通过。
4. 准备并登记测试数据、租户、账号、Token、时间基线。
5. 确认可观测性入口可用：应用日志、审计日志、性能指标、trace 或等价追踪能力。

### 6.2 执行顺序

必须遵循以下顺序：

1. **环境基线校验**
2. **契约校验**
3. **集成校验**
4. **E2E 用户路径校验**
5. **运行时一致性校验**
6. **负路径与安全约束校验**
7. **失败复核与分类**
8. **人工确认与最终判定**

禁止跳步，除非上一步已明确判定为 `env` 阻塞。

### 6.3 每次执行必须收集的证据

每条关键 Claim 至少收集以下证据：

- 原始输入
- 请求与响应摘要
- 关键页面截图或 DOM 快照
- 运行日志摘录
- 审计记录摘录
- trace / request 关联标识
- 开始时间、结束时间、执行耗时
- 环境标识与版本号
- 执行命令或可重放步骤

### 6.4 必须执行的复核动作

- 关键失败至少复跑一次
- 涉及并发、缓存、过期、权限、TEE 状态切换的场景，必须换数据或换会话复核
- 安全类断言必须同时验证“拒绝结果”和“审计留痕”
- 性能类断言必须看分布，不允许只看一次最好值
- UI 类断言必须对照 API 或审计侧证据，禁止只看页面文本

### 6.5 当前系统的强制验收关注点

结合 CredBridge 当前架构，以下内容必须纳入验收：

- TEE 模式与仪表板呈现是否一致
- Attestation 接口与运行态摘要是否一致
- PASETO 认证与租户隔离是否成立
- PostgreSQL RLS 与 API 返回结果是否一致
- 审计日志是否对关键安全动作形成闭环
- Token、凭证、沙箱、审计、仪表板之间的数据是否一致
- 前端控制台展示与后端事实是否一致，不能出现“页面健康但后端失真”

## 7. 禁止事项

以下行为在系统验收中一律禁止：

### 7.1 用低层证据冒充高层验收

- 禁止用单元测试通过直接宣告系统通过验收
- 禁止用 lint、clippy、类型检查、代码 review 结论直接宣告运行时正确
- 禁止用 mock 环境结果宣告真实依赖集成成立

### 7.2 用实现细节代替外部事实

- 禁止通过读取内部状态、私有字段、CSS class、函数名来证明用户可见行为
- 禁止只看数据库记录而不看 API / UI / 审计外部表现
- 禁止只看前端展示而不核对后端事实

### 7.3 用取巧方式制造“通过”

- 禁止人工修改测试数据来绕开真实校验逻辑后再宣告通过
- 禁止删除失败样本、只保留成功样本
- 禁止只展示最好一次性能结果
- 禁止手工编辑日志、截图、报告、trace 以美化结果
- 禁止因重试通过而隐去初次失败

### 7.4 用不受控环境替代目标环境

- 禁止用本地 simulation 结果替代硬件 TEE 验收结论
- 禁止用开发 stub 服务替代真实外部依赖后宣告联调通过
- 禁止跨版本、跨配置、跨数据集外推结论

### 7.5 未分类失败直接定责

- 禁止把所有失败都打成产品缺陷
- 禁止把无法解释的失败静默归零
- 禁止带 `unknown` 或未复核的 `flake` 进入最终通过结论

## 8. 验收出口准则

只有在以下条件全部满足时，才能给出“验收通过”：

1. 所有 P0 Claim 已完成 `Contract + Integration + E2E + Runtime` 证据覆盖
2. 不存在未分类失败
3. 不存在未处置的高风险 review finding
4. 不存在未解释的前后端事实不一致
5. 关键安全动作均有审计留痕
6. 关键运行时结论均可追溯到原始工件
7. 必须人工确认的项已经完成签署

下列情况只能给出“有条件通过”：

- 非 P0 Claim 存在明确记录的缺口，但不影响当前发布目标
- 存在已知低风险问题，且有明确回补计划与责任人

下列情况必须判定为“不通过”：

- 任一 P0 Claim 失败
- 存在 `unknown` 结论
- 关键审计、隔离、TEE、认证结论缺少运行时证据
- 使用了本规范列明的禁止动作

## 9. 与现有开发门禁的关系

以下检查仍然是仓库硬门禁，但它们属于 **代码质量准入**，不是 **系统验收事实**：

```bash
cargo fmt
cargo clippy --tests -- -D warnings
cargo test
```

前端构建与静态检查同理：

```bash
cd frontend
npm run build
npm run lint
```

原则：

- 这些检查失败，版本不得进入验收
- 这些检查通过，也**不得**直接宣告系统验收通过
